# SchemaRouter 0.10.0

SchemaRouter 0.10.0은 consolidation release입니다.

Open-set routing research가 끝났다고 주장하지 않습니다. 여러 research cycle 뒤 product boundary, stable implementation, scientific data contract, current benchmark evidence를 명확히 정렬하는 것이 목적입니다.

## Product model

SchemaRouter를 agent/RAG application과 registered API/tool 사이의 **typed capability retrieval and execution layer**로 정의합니다.

RAG는 **Retrieval-Augmented Generation**입니다. Generator가 external source에서 retrieve한 정보로 보강됩니다. SchemaRouter 자체는 complete generation architecture가 아닙니다. External source가 API/tool일 때 RAG/agent system에 structured retrieval/execution boundary를 제공할 수 있습니다.

```text
RAG / Agent
    -> declare external data need
SchemaRouter
    -> retrieve registered capability
    -> select endpoint + fields
    -> validate and execute
    -> return typed external data
RAG / Agent
    -> generate or reason with that data
```

LangChain/LangGraph/LlamaIndex/application은 위에 있고 OpenAPI/MCP/OPTIMADE/Python tool/approved plugin은 아래에 있습니다. Autonomous agent loop가 되지 않습니다.

## Stable architecture

Default product path:

```text
request
  -> semantic field need
  -> registered candidate recall
  -> bounded route selection
  -> policy / health / evidence checks
  -> parameter + field plan
  -> raw schema validation
  -> optional declared unit normalization
  -> local field projection
  -> typed ToolResult
```

Optional decision backend는 registered candidate에 대한 bounded selection을 도울 수 있지만 execution authority를 받지 않으며 development benchmark 개선만으로 unconditional default로 promote되지 않습니다.

## Typed data contracts

Registered field는 다음을 가질 수 있습니다.

- JSON datatype/shape
- semantic ID와 trusted alias
- source unit
- 명시적인 `UnitNormalizationSpec` 차원·정규 단위·배율·오프셋
- temperature/pressure/phase/orientation/measurement method 같은 exact qualifier
- 선언된 출처·라이선스·원본 유형 근거

Unit은 optional입니다. Text, identifier, boolean, structured metadata, dimensionless number는 unitless일 수 있습니다.

Cross-provider fallback은 conservative합니다. Trusted code가 선언하지 않은 scientific equivalence/unit conversion을 추론하지 않습니다.

## Generic capability registration

Benchmark-specific route configuration이 아니라 generic registration이 의도된 UX입니다. Native `ToolSpec`, OpenAPI, MCP, OPTIMADE, Python capability를 동일 typed registry model로 normalize합니다.

첫 registry-compiled capability-verifier prototype도 canonical DEV와 previously unseen native/OpenAPI/MCP registration holdout에서 평가했습니다. Provider-neutral typed compiler는 동작했지만 synthetic learned veto가 supported request를 과도하게 reject했습니다. Exact routing은 canonical DEV 5.03%, registration holdout 2.08%로 떨어지고 false-route는 0%였습니다. Terminal reject되었으며 0.10.0 default에 포함하지 않습니다.

## Routing benchmark: current evidence

0.11 architecture-search cycle은 promoted production-target candidate 없이 종료됐습니다.

장기 목표: 지원 요청의 정확 경로 선택률 >=85%, 근접 도메인 미지원 요청 거부율 >=97%, 분포 밖 요청 거부율 100%, 잘못된 경로 선택률 <=1%, 권한·실행 오류 0건, 실행 가능한 경로의 p95 지연시간 <=250 ms.

Strongest executable DEV candidate: **85.07 / 99.31 / 100 / 0.62**, p95 176.94 ms. Unchanged zero-overlap fresh confirmation: **84.81 / 90.45 / 100 / 8.49**, p95 278.37 ms. Fresh result가 promotion을 실패해 calibration/blind-final은 소비하지 않았습니다.

Conservative #259 profile은 **83.77% supported exact**, **98.96% near-domain rejection, 0.93% false-route**, 약 **134.95 ms** p95의 useful reference지만 target pass로 relabel하지 않습니다.

현재 해석은 [Routing research status](../research/routing-status.md)를 참고하십시오.

## Bounded decision ecosystem

0.10.0은 replaceable decision-provider surface도 통합합니다.

- explicit third-party `schemarouter.decision_backends` entry point
- provider-neutral `CallableDecisionBackend`
- planner-specific model class 없는 System-One/Jev-compatible provider configuration
- secret을 노출하지 않고 provider/model config를 기록하는 benchmark/report metadata
- evidence-preserving optimization용 runtime-parity/freeze-manifest infrastructure

Provider compatibility는 model이 default가 될 만큼 safe/accurate하다는 evidence가 아닙니다.

## Compatibility

Pre-1.0입니다. Orchestration, memory, conversation state, autonomous tool loop를 package 안으로 이동시키지 않습니다.

Deterministic routing 또는 optional bounded decision backend를 쓰는 기존 application은 experimental capability-verifier path를 채택할 필요가 없습니다.

## Release validation

Protected release pipeline은 Python 3.10–3.14, Windows smoke, minimum dependencies, Pyright, branch coverage, wheel/sdist, optional integrations, docs, security analysis, SBOM/provenance, exact post-publish PyPI verification을 포함합니다.
