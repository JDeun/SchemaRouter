# SchemaRouter 제품 설계 헌장·근거 정렬·검증 로드맵

**판단 기준일: 2026-10-16 · 설계 정렬 문서 · 새 성능 검증 또는 출시 승인이 아님**

이 문서는 새 세션에서 반드시 읽는 **제품·검증 판단 기준**입니다. 이미 확정된 공개 API를 폐기하거나 새 프레임워크로 처음부터 재설계하자는 문서가 아닙니다. [설계 원칙](../concepts/design-principles.md), [SchemaRouter란?](../concepts/schema-router.md), [Stable Core](../stable-core.md), [아키텍처 및 신뢰 경계](../architecture.md), [전체 실험 인덱스](experiment-index.md), [오픈소스 기존 조사 위키](tool-routing-landscape.md)와 함께 읽습니다. 오래된 문서가 특정 이슈를 `진행 중`이라고 표현하면 해당 기록 시점과 2026-10-16 현재 상태를 구분합니다. 실제 원본 실험·동결된 점수·아티팩트가 이 요약 설명보다 우선합니다.

## 1. 목적과 제품의 존재 이유

**목적:** 호스트 애플리케이션이나 AI 에이전트가 API·MCP·도구·데이터 시스템에서 **원본에 등록된 진짜 기능**을 발견하고, 필요한 기능과 필드를 확인하고, 가장 작은 정당화된 호출 집합을 계획한 다음, **호스트가 통제하는 권한·검증·실행 경계** 아래에서 안전하게 사용하도록 돕습니다.

**목적이 아닌 것:** 별도의 자율 에이전트 전체 구현, 채팅 메모리·그래프 실행기, LLM 가격/성능 모델 라우터, MCP·Pydantic AI·LangGraph·LlamaIndex의 수명주기 교체, 실행 가능한 스키마 임의 생성, 모델 검색 점수에 의한 실행 권한 부여입니다.

**차별화할 제품 가치:** 흔한 검색기는 `질문 → 관련 도구`에 집중하지만, SchemaRouter는 `질문 → 논리적인 데이터·작업 필요 → 필수 입력·출력 필드 → 현재 허용된 도구·엔드포인트·제공자·접근 방식 → 상한이 있는 타입 기반 계획 → 검증된 호출 → 검증되고 최소화된 결과`를 책임집니다. 상위 에이전트는 사용자 목표·대화·멀티스텝 흐름을, 로컬 호스트는 정책·자격증명·원본 등록·실행·승인을 담당합니다.

## 2. 성능 최적화를 위해서도 절대 깨뜨리면 안 되는 원칙

| 불변 원칙 | 구현상 의미와 위반 시 동작 |
| --- | --- |
| **원본 출처가 모델보다 우선** | 실행 가능한 정체성은 등록된 `ToolSpec`·`EndpointSpec` 또는 검증된 어댑터 출처에서만 옵니다. 원본 fingerprint·레지스트리 버전으로 다시 검증 가능해야 합니다. 모델이 새 엔드포인트·필드·권한·별칭을 만들어서는 안 됩니다. |
| **필드와 작업은 타입 계약** | 필수 입력과 제공 가능한 출력, `semantic_id`, 데이터 타입, 단위·물리적 한정 조건, 부작용 종류, 제공자·접근 방식을 구분합니다. 의미 유사도가 높아도 필요한 기능이나 필드가 없거나 단위가 다르면 선택할 수 없습니다. |
| **권한은 검색 전 적용** | 호스트의 Principal·RBAC·ABAC, 데이터 범위 및 숨긴 필드, 로컬 가용성은 외부 모델에 후보를 보내기 전에 반영합니다. 숨겨진 도구와 설명문·개수의 누출을 허용하지 않습니다. 공개 `total_ranked`는 **권한 범위 내 양수 점수·Top-K 이전 수**이지 전체 허용 레지스트리 완전성 증명은 아닙니다. |
| **검색 결과는 실행 허가가 아님** | 검색과 모델 제안은 참고 후보만 반환하며, 검색 실험에서는 제공자 도구를 실제 호출하지 않습니다. 나중에 호스트가 인자 JSON Schema, fingerprint, 신뢰된 실행 바인딩, 정책, 승인, 재시도·예산, 원본 결과 검증과 필드 투영을 재확인합니다. |
| **자원 한도는 명시적** | K, 허용 호출 수, 공개 스키마 바이트·토큰, 지연시간, 메모리, fallback 너비를 성능 수치 개선을 위해 몰래 늘리지 않습니다. **모델 입력 바이트·공개된 도구 스키마 바이트/토큰·에이전트 전체 토큰**은 다른 분모입니다. |
| **미지원·정보 부족·모호함·권한 없음·일시적 사용 불가 구분** | Top-K 결과가 비어 있거나 모델이 선택을 거부한 사실은 보정된 미지원 분류가 아닙니다. 미지원 요청 오선택(false accept)과 정상 요청 오거부(false refusal)를 별도 측정합니다. 새 독립 데이터로 보정·확인하기 전 제품 no-fit 판정으로 승격하지 않습니다. |
| **실패와 근거를 삭제하지 않음** | 보안 정책 우회, 허구의 작업 완료, 부정적인 연구 결과 삭제, 동결된 평가 데이터로 재튜닝, 평가 후 정답 수정, 합성 E0 또는 공개 DEV를 외부 독립 E2로 홍보하는 행위를 금지합니다. |
| **작고 상호운용 가능한 기본 코어** | 기본 Python API는 CPU 사용과 결정성을 유지하며 불필요한 선택적 의존성을 강요하지 않습니다. 다국어 모델·원격 서비스·벡터 검색·외부 프레임워크는 증거가 확보되기 전까지 교체 가능한 opt-in이어야 합니다. |

**Stable Core 계약:** `SchemaRouter.retrieve/aretrieve` 및 실행 준비·상태 인식 변형은 읽기 전용 기능 발견 인터페이스입니다. 기존 계획·실행·통합 모듈의 책임을 유지하며, 벤치마크 점수가 조금 올랐다는 이유만으로 [안정화된 코어 계약](../stable-core.md)을 재설계하지 않습니다. 외부 SDK에는 SDK 고유의 승인·실행·수명주기가 남아 있어야 합니다.

## 4. 하나의 통합 파이프라인 — 설계 가설이며 제품 채택 결정이 아님

`호스트가 인증한 EN/KO/JA 요청 → (A) 등록된 원본·권한·데이터 범위 내 후보 → (B) 재현 가능한 Lexical/BM25와 선택형 다국어 Dense로 후보 검색 → (C) 원본 ID 기반 고정 K 후보 통합 → (D) 등록된 작업·필수 입력·출력 필드의 타입/의미 적합성 확인 → (E) 독립 보정된 미지원·모호함·정보 부족 분기 → (F) 상한 내 스키마만 하위 에이전트에 공개 → (G) 실행 직전 권한·원본·인자·근거·승인 재검증 → (H) 멀티스텝 작업과 최종 답변 평가`.

파이프라인을 서로 다른 **4개 질문**으로 나눕니다.

- **발견(Discovery):** 허용된 원본 도구에서 모든 필수 기능을 최대 K개 후보 안에 포함했는가? 숨긴 도구는 노출하지 않았는가?
- **적합성(Fit):** 후보가 해당 작업과 **필수 입력·출력 필드**를 실제 제공하는가? 단위·부작용·의존 관계가 맞는가?
- **판단(Disposition):** 실제 실행 가능, 정보 추가 필요, 미지원, 권한 없음·현재 사용 불가 중 어느 상태인가? 오거부나 오선택이 있는가?
- **작업 효용(Agent utility):** **동일한 에이전트**에 도구를 넘긴 후 안전하고 정확하게 전체 작업을 완료했는가? 최종 답변·출처·도구 호출의 품질이 유지되고 실제 자원 비용이 줄었는가?

유사도 점수나 단발성 LLM 응답을 이 네 단계 중 하나의 독립적인 승인 근거로 몰래 대체하지 않습니다.

### 새로운 평가를 만들 때 최소 포함할 과제 유형

여섯 종류를 영어·한국어·일본어(가능하면 스페인어·독일어·혼합 언어도)에 분산합니다. **(1)** 필수 인자가 있는 단일 원본 read endpoint, **(2)** 서로 다른 도구로 채워야 하는 필드 합집합, **(3)** 상태가 변하거나 식별자를 전달하는 연속 2~3단계 작업, **(4)** 같은 도메인 read/write/delete 형제 작업 구별, **(5)** 필드 부족·정보 부족·모호한 요청, **(6)** 실제 미지원 및 관련성이 높은 OOD. 카탈로그 크기는 100/250/500개, 독립 원본 제공자는 2곳 이상을 목표로 하되 실제 허용된 데이터를 기준으로 합니다.

**성공률·사례 수를 결과를 보고 나서 정하지 않습니다.** 새로운 독립 데이터의 실제 확보 수, 통계적 불확실성, 일차 평가 지표, 비용 상한, 승격 기준을 채점 전에 명시합니다. 동일 과제를 카탈로그 크기별로 반복한 결과를 서로 독립인 샘플처럼 세지 않으며 출처와 권한·정답의 근거를 남깁니다.

### 실패가 나타났을 때 다음으로 고칠 부분

| --- | --- |
| 정답 도구가 원본의 권한 내 후보 목록에 없음 | 원본 도구 등록·스키마·필드 선언·RBAC/ABAC·가용성 |
| 정답 도구는 허용됐지만 한국어/일본어 Top-K에 누락 | 토큰화·별칭·다국어 후보 표현·고정 K 검색 |
| 정답 도구는 Top-K에 있는데 작업/인자가 틀림 | 입력·출력 타입·작업 적합성·결정 백엔드 선택 규칙 |

## 6. 앞으로 연구를 시작하고 멈추는 운영 규칙

**새 프레임워크나 모델 비교를 열기 전에 다음을 확인합니다.**

1. 이 설계 헌장, [실패·오픈소스 조사 위키](tool-routing-landscape.md), [선행연구](prior-art-roadmap.md), [과거 전체 실험](experiment-index.md), [#200](https://github.com/JDeun/SchemaRouter/issues/200)·[#1339](https://github.com/JDeun/SchemaRouter/issues/1339)·[#1346](https://github.com/JDeun/SchemaRouter/issues/1346)·[#1450](https://github.com/JDeun/SchemaRouter/issues/1450)의 중복·완료·외부 차단 상태를 먼저 읽습니다.
2. 이번 변경으로 고칠 **정확한 실패 하나**, 합법적으로 볼 수 있는 원본·문제·권한, 기존 연구와의 중복 여부, 비교 기준과 **동일 K·스키마 예산**을 문서로 확정합니다.
3. 점수를 보기 전에 문제·원본 정답을 잠급니다. **E0 합성·통합 계약**, **E1 실제 제공자이지만 연구자가 이미 본 DEV**, **E2 새로운 독립 원본·전체 에이전트 작업 검증**을 혼합하지 않습니다.
4. 먼저 가장 작은 단위의 원인 재현을 합니다. 실패 원인을 설명하지 못하면 비슷한 연구 PR을 늘리지 않고 **중단**합니다.
5. 실제 최종 작업 성공률과 미지원·오거부·권한·자원비용 기준까지 함께 충족할 때만 새 기능 승격을 논의합니다. 위조된 성공 판정, 기본 E5 임의 승격, 동결된 평가 수정, v0.18 임의 태그 생성은 허용하지 않습니다.

**2026-10-16의 판단:** 타입 기반 기능 라우팅·정책이 통제하는 실행이라는 아키텍처는 유지합니다. 이미 구축한 코드·연구를 우선 재사용하고, 앞으로는 **후보 검색 → 타입 적합성 → 분리된 미지원 판단 → 실제 작업 완료**로 이어지는 하나의 검증 가능한 파이프라인에 집중합니다. 핵심 구조는 비교적 성숙했지만, **여러 제공자와 언어에서 일반화되는 작업 성공률과 신뢰할 수 있는 미지원 판정은 아직 입증되지 않았습니다**.
