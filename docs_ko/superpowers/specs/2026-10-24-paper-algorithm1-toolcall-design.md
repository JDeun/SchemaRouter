# 원 논문 Algorithm 1 — 출처 검증 기반 ToolCall 투영 (P2 첫 단계)

**결정:** P1에서 이미 증명한 `PaperFieldCoverage`를 호스트 전용·명시적 선택 방식의 `ToolCall`로 투영합니다. 원본 경로 식별자, 필드 및 생산자→소비자 입력 의존성을 정확하게 보존합니다. 이는 #1560의 첫 구현 단계이며 Algorithm 1 전체나 실행 가능한 다중 호출 오케스트레이션을 완성했다는 의미가 아닙니다.

## 목표와 한계

원 논문은 검색 결과를 도구, 엔드포인트, 인자, 응답 필드, 근거를 포함한 계획으로 구성합니다. 현재 P1은 모든 요구 필드의 충족을 증명하는 변경 불가능한 경로 기록까지만 제공합니다. 다음 단계에서는 호스트가 필요한 호출 순서를 확인할 수 있도록 해당 기록을 기존 `ToolCall` 모델과 연결합니다. 이를 위해 라우터가 데이터에 의존하는 인자를 추측하거나 새로운 에이전트를 실행하게 만들지 않습니다.

호스트가 나중에 명시적으로 호출하더라도 기존 권한 검사와 실행기 검증을 반드시 통과해야 합니다. 검색 및 투영 과정 자체는 등록된 도구를 호출하지 않고, 권한을 부여하지 않으며, 기존 `plan`·`retrieve`·`execute` 동작이나 그래프·인덱스를 변경하지 않습니다. 생산자 응답이나 아직 연결되지 않은 후속 호출 인자를 이미 확보한 것처럼 취급하지 않습니다.

## 검토한 구현 방식

1. **선택: P1 필드 증명에 기반한 명시적·비실행 `ToolCall` 구성.** 직접 호출에서는 이미 선정된 출처 가시 필드명을 그대로 사용합니다. 1-hop과 동일 루트 분기에서는 아직 값이 없는 의존 인자와 구조화된 바인딩 기록을 함께 유지하고 원본 생산자·소비자 `ToolCall`을 순서대로 구성합니다. P1이 검증하고 호스트가 명시적으로 승인한 입력 필요 G5 루트는 필수 호스트 입력명을 **미충족** 상태로 표시할 수 있지만 값은 넣지 않습니다. 기존 `SchemaPlanner._evidence`와 `ToolCall`을 재사용하며, 별도의 Top-K 재선정을 통해 다른 경로가 선택되지 않도록 합니다. 장점은 원본 출처 선택을 유지하면서 논문의 출력 구조를 통합한다는 점입니다. 실제 호스트 입력값 연결과 실행은 아직 범위 밖입니다.
2. **보류: 선택된 모든 단계를 다시 `SchemaPlanner.plan`으로 라우팅.** 현재 순위 시스템은 P1 기록의 특정 권한 검증 엔드포인트를 고정할 수 없어 다른 경로를 반환할 수 있습니다. 별도 경로 고정 계약 없이 안전한 컴파일 방식으로 사용할 수 없습니다.
3. **제외: 새로운 실행 그래프나 에이전트 파이프라인 생성.** 이미 있는 G5 기능과 중복되며 구조적 입력 연결을 실제 인자 값으로 잘못 승격시킬 위험이 있습니다.

## 인터페이스 및 안전 계약

`compile_paper_field_toolcalls(router, query, *, principal, catalog, index, k=5) -> PaperFieldToolCallPlan`은 P1과 동일한 결과 상태, 스냅샷, 레지스트리 버전 및 제한된 대안을 반환합니다. 완전한 대안은 출처→소비자 순서의 기존 `ToolCall` 튜플과 단계 인덱스로 표현한 `PaperFieldArgumentDependency` 기록을 포함합니다. 의존 호출은 원본에서 바인딩될 입력명을 `missing_required_arguments`에 두고 `arguments`는 비워 둡니다. 따라서 해당 `ToolCall.executable`은 거짓입니다. 입력이 없는 출처 호출에는 인자를 만들지 않습니다. 입력이 필요한 루트는 원래 G5 인덱스의 명시적 호스트 승인과 정확한 `_host_source_input_names` 계약을 충족해야 합니다. 이 경우에도 `post_id`와 같은 입력값은 **미충족** 상태이며 루트는 실행 불가입니다. 전체 결과의 `executable_authority=False`는 유지되고 API 내부에서는 호출을 실행하지 않습니다.

컴파일러는 원본 `ToolSpec`와 현재 주체에게 허용된 `EndpointSpec`을 다시 읽어 권한 정책, 지문, 가용성, 읽기 전용 속성, 필드 가시성을 검증합니다. 모든 바인딩은 앞 단계의 호출, 선언된 소비자 인자, 원본 생산자 출력 필드를 참조해야 하고 대상 인자가 중복되면 안 됩니다. 반환 직전에 P1 증명을 다시 수행해 동일성을 확인합니다. 불일치가 있으면 결과를 차단합니다. 단, 두 번째 관찰로 여러 공급자에 걸친 원자성을 보장할 수는 없습니다.

이 단계가 지원하는 범위는 P1에서 검증된 무입력 호출, 호스트 승인 G5 입력 루트의 **기술용 기록**, 1-hop 및 동일 루트·두 소비자 분기입니다. 현재 미검증 OPTIMADE 검색 인자는 보류합니다. 구체적이고 완전한 호스트 입력값 바인딩과 기존 실행기를 통한 실제 실행은 별도 검증된 확장 단계에서 구현해야 합니다. 외부 데이터클래스는 고정돼 있지만 내부 Pydantic `ToolCall`의 필드는 여전히 변경할 수 있으므로, 결과를 변조 불가능한 영구 인증 기록으로 취급해서는 안 됩니다. 품질 검증, 출처 독립 E2, 운영 기본값 및 v0.18 배포 보류 상태도 유지됩니다.
