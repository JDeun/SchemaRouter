# #1339 P0 operation-identity scoring vs description-only E5-base at original K5

**2026-10-19 pre-registered before any model result.** Dependent on merged [#1609](https://github.com/JDeun/SchemaRouter/pull/1609), which measured real pinned E5-base CPU on a different 24-case self-authored cohort: EN 6/6 Top5, KO 6/6, JA 5/6, unsupported 2/2 per language returning K5. The previous failed Japanese material.units request is **not** included in this new manifest and cannot be silently reused as a training example or threshold.

## Independent variable and falsifiable hypothesis

The prior CPU model-selected candidates relied on the original native route label and endpoint description. The Japanese unit-vs-measurement confusion might be partly related to insufficient weight on the **actual endpoint operation name** (e.g., source-authored `materials.units` vs `materials.search`), even if the model recognizes the subject area. Could an opt-in source-only scoring channel improve supported Top1/Top5 without introducing aliases or increasing total query encoding latency excessively?

- A: fixed E5-base `query:` embedding against exact original comparator label+description text `route_id + "\n" + scoped_description`, cosine ranking.
- B: same query embedding and same A cosine plus `Operation name: {endpoint name}` *derived from original source route ID only*, weighted **0.75 A cosine + 0.25 operation-name cosine**. One global predetermined weight across EN/KO/JA, positive/negative and all 500 routes, never tuned on this cohort or #1609. The same true English-only 500 authorized native routes, original provider identities and SHA256 are required. Original source fingerprints and route order are checked after capture. All operations are read-only.
- Both use the same E5-base revision `d13f1b27baf31030b7fd040960d60d909913633f` on Ubuntu Python3.12 CPU, `trust_remote_code=False`, the exact original scoped-query+passage E5 prefixes. Verify A first-query fixed-K5 against existing `AuthorizedFixed5DecisionSelector` using a real model; abort if representation differs.
- Static first-request stage encodes **1000 passages (500 original full descriptions + 500 derived original operation names)** once, then both arms use the same query vector, original source/fingerprints and fixed K5. Report this *one-time index-build CPU cost* separately from warm query/score p50/p95. Do NOT equate this cache-backed query measurement with the previous 500-route full source-capture/model selector latency or a production p95 target.
- The **NEW** developer-authored 24 task manifest is in `scripts/research_source_operation_channel_e5_base_cpu_dev.py`: 6 supported and 2 unsupported tasks per EN, KO, JA. Exactly six native expected canonical routes spanning materials measured values, measurement units, papers DOI citation, papers search, flight status and foreign-exchange history. All queries are newly written, but these same route categories were inspected previously: **author DEV, not independent blinded E2**. No answer-key or translation is encoded in model input. No current/future score-based change to the manifest.
- Negative requests all remain unsupported; both fixed K5 arms unconditionally return 5 original route IDs and MUST record `unsupported_nonempty=2/2` per language. This is explicitly a failed/no-fit-uncalibrated system property, **not successful rejection**. No threshold learned or production default changed.
- Critically the current legacy synthetic 500 route fixture has **zero declared native FieldSpec output schemas**. It cannot measure required-output-field fit, typed arguments or unit selector execution. We therefore name the independent variable *operation name*, never claim source field-typed fit. That must be qualified separately on actual OpenAPI/MCP/OPTIMADE source authoring. Actual execution and grounded final answers are future #1477 / #1346 work, not part of this experiment.
